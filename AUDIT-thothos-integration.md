# Capability Audit — Network-Monitor ↔ ThothOS-ai-native Integration
## Synthesis Verdict

---

## 1. Does the setup make sense?

**Verdict: The architecture is sound and correctly aimed; the implementation delivers roughly 1.5 of its 5 data planes. As shipped to a buyer today, the integration is a config viewer plus a heartbeat — not a monitoring product — and the published agent cannot even complete registration.**

Strongest reasons the design DOES make sense:

1. **The wire contract is genuinely solid.** All 20 GraphQL operation names, args, response fields, and the full Bearer-`tk_` auth chain (bcrypt validate → CSRF exemption → userType-gate skip → scope check → tenant binding) verified matching end-to-end across both repos (coverage: `contract:proxy-lifecycle`, `snmp-family`, `icmp-family`, `oid-bidirectional`, `ipam-family` — zero op/arg/auth mismatches). Registration upserts on `(companyId, apiKeyId)` and `(companyId, name)` are restart-idempotent by design (`proxy.entity.ts:424-456`, `webhook.entity.ts:141-193`). This is a well-built seam at the transport layer.
2. **The data-flow direction is right for the AI-native rebuild:** ThothOS as the multi-tenant config/control plane (entity manifests, workspace adapters, chat-buildable activation via `platform_enable_workspaces` — `platform-builder-tools.ts:110-153`, `slugs.ts:55-59`) and NM as an on-prem execution proxy is the correct hub-and-spoke shape. The workspace itself follows every rebuild invariant (presentational view, dual demo/live adapters, registry ref, parity-by-identity).
3. **Both endpoints are individually real products:** ThothOS's workspace is full CRUD over ICMP/SNMP/IPAM/inventory/API-keys with working one-time `tk_` minting; NM's local engines (pro-bing ICMP, gosnmp v1/v2c/v3, 30s alert state machine, real gRPC bandwidth streaming) are real code, not stubs.

Why it fails capability-wise TODAY: the two middle planes were never wired. Config flows down but dies in a write-only in-memory cache that nothing reads (`webhooks.go:125-203` getters: zero callers); results never flow up (the entire NM→ThothOS surface is 6 mutations, and the only recurring one carries 5 scalars — `client.go:214,299,499,539,580,906`; `main.go:736-754`); and the push channel is broken at four independent layers. The product promise ("configure monitoring in ThothOS, proxy executes, results report back" — `README.md:45`) does not exist in code.

- **The entire GraphQL wire contract** — op names, endpoints, args, response shapes, envelope, error mapping — matches for all 20 operations across proxy/webhook/snmp/icmp/ipam families. No OP-MISSING, ARG-MISMATCH, or AUTH-MISMATCH anywhere.

- **Key minting, both paths:** dashboard one-time-rawKey modal (`proxy.helpers.ts:23-50`, shown once, bcrypt-hashed) and the MFA flow (TOTP + brute-force lockout + server-resolved tenant, CF-157).
- **Registration idempotency:** registerProxy and registerWebhook upserts make restarts and retry double-fires harmless; webhook secret persists encrypted and restores at boot (`main.go:207-212`).
- **Field crypto both sides:** symmetric encrypt-at-rest/decrypt-on-read for proxy IPs, SNMP credentials, IPAM addresses, webhook secrets; NM's `v1:` envelope is idempotent and plaintext-tolerant.
- **NM's local engines are real:** ICMP/SNMP polling, alert state machine with duration/dedup/auto-resolve, gRPC bandwidth testing with genuine byte counting, discovery sweep, ~2000 lines of real network tools, DB-backed reports, checksum-verified self-updater. The NM-side HMAC/replay receiver logic is internally correct (the break is cross-repo, not local).
- **The ThothOS workspace + builder fit:** full employee CRUD across all five sections, 21-dataset RSC prefetch, dual-adapter parity-by-identity, chat activation and block-mount of the workspace both work. Standalone single-tenant NM mode is coherent end-to-end (modulo the boot-freeze restart ritual).
- **Heartbeat transport** (`proxyHeartbeat` mutation, tenant-bound, counts surfaced on the proxy card) works whenever the boot path starts it.

## 4. Highest-leverage fixes

**Fix 1 — Ship the seam. (unblocks every buyer; ~1 day)**
Commit the 2026-06-13 Network-Monitor working tree (callback pre-screen in `internal/thothos/client.go`, `ipam/ip-address` path fix, webhook-secret persistence in `main.go`/`internal/api/webhooks.go`, the 9 untracked `*_test.go`), push `production`, cut a tagged release with `-ldflags "-X main.version=..."`, and change the wizard (`ThothOS-ai-native/src/workspaces/network-administration/proxy/index.tsx:1097,1164`) to download the tagged release (prebuilt binary if possible) instead of the moving branch zip. Without this, every other fix is invisible to buyers.

**Fix 2 — One connect routine, one liveness truth. (makes the only live channel honest)**
NM: extract `startThothOSSession(ctx, client, cfg)` in `main.go` doing register→webhook→pull→`startHeartbeat` under a cancelable context, and call it from all three entry points (boot branch `main.go:227+`, `auth.go:registerWithThothOS`, `settings.go:registerProxyWithThothOS`); have disconnect (`settings.go:268-278`) and logout (`auth.go:566-580`) cancel the context, delete the ProxyConfig row, and set standalone — killing the wizard-never-heartbeats, cosmetic-disconnect, logout-brick, and hybrid-MFA-state findings in one refactor. ThothOS: add `src/app/api/cron/mark-stale-proxies/route.ts` calling `markStaleProxiesOffline()` + a `vercel.json` cron entry (the 8-cron pattern already exists).

**Fix 3 — Kill the push channel; make pull operative. (deletes 4 broken layers, wires the dead plane)**
Drop webhooks for v1 (remove the three `RegisterWebhook` calls, the receiver, and ThothOS's dispatch of never-consumed events — or leave dispatch for proxy.* only). Replace with a 60-120s config re-pull ticker in `main.go` that, instead of writing ConfigCache, runs an **apply step**: persist templates to SQLite models and push interval/threshold changes into the collectors via their existing-but-uncalled `SetInterval`/`AddDevice`/`RemoveDevice`. Pass the collector handles into `api.NewServer` so `devices.go` create/delete wire devices live (fixes boot-freeze). Make `/monitor/sync` and `/ipam/sync` call the same apply step or return honest "fetched, not applied". Delete ConfigCache. This converts "configuration theater" into a config-driven proxy and gives offline capability for free (persisted config).

**Fix 4 — Build the results-up channel. (the actual product; largest single feature)**
ThothOS: new `src/lib/entities/network-administration/results.entity.ts` (or a bulk-ingest REST route) consuming the already-minted `metrics:write` scope — device status transitions + rollup latency/loss, tenant-bound like proxyHeartbeat. NM: a reporter goroutine batching poller results (the poller already writes status/latency to gauges and DB — `poller.go:183-197`) every 30-60s. Surface it on the proxy card / a status tab. Until this exists, do not claim "results reported back to ThothOS" — fix README:45 either way.

**Fix 5 — Stamp companyId in NM create paths. (un-blinds integrated mode)**
In `registerNode` (`nodes.go:345-414`), `createDevice` (`devices.go:108-127`), `createAlertRule`, discovery inserts, and `TriggerAlert` (`engine.go:231-242`): stamp `middleware.GetCompanyID(c)` (or the global context) instead of persisting `''`/client-asserted values; make the node update path repair CompanyID; add a unique index on Node.Name (or key registration on name+company). Also make the sweep re-assert `last_seen < cutoff` in the DELETE and add heartbeat-driven re-registration on 404. Without this, the node/bandwidth subsystem is unusable for exactly the connected buyers the integration targets.

**Bottom line for the owner:** keep the architecture — the seam engineering (contract, auth, idempotency, crypto) is better than most of what sits on top of it. The failure is that both repos built their half of three data planes (config-apply, results-up, push) to the wire and stopped; nothing was ever wired end-to-end, and nothing at HEAD is shippable because the one registration-breaking fix lives only in an uncommitted working tree. Fixes 1-3 are days of work and convert the integration from demo-ware to a truthful (if modest) config-synced monitor; Fix 4 is the feature that makes it a sellable monitoring product.

## [P1-broken] HMAC signature scheme mismatch: every ThothOS webhook dispatch is rejected 401 by the proxy receiver, then auto-disabled server-side
source: contract:webhook-realtime
ThothOS signs the RAW BODY ONLY: dispatch.ts computes signature = HMAC-SHA256(secret, payloadString) and sends it as X-Webhook-Signature — but it ALSO unconditionally sends X-Webhook-Timestamp on every dispatch. The Go receiver branches on that header's presence: `if timestamp != "" || requireTS` enters the replay-protected path, which requires the signature to be HMAC-SHA256(secret, timestamp + "." + body) (computeWebhookHMACWithTimestamp). Body-only signatures can never equal timestamp-bound ones, so verification fails 100% of the time and the receiver returns 401 'Invalid signature'. The legacy body-only verification branch (webhooks.go:373) is unreachable for ThothOS senders because the timestamp header is always present. Compounding: each 401 makes ThothOS call recordWebhookFailure ($inc failureCount); getWebhooksForEvent filters failureCount<5, so after 5 attempts the webhook silently drops out of dispatch entirely. The timestamp itself would parse fine (Go time.Parse RFC3339 accepts toISOString() fractional seconds) — the pre-image composition is the sole break, and it breaks the push path in EVERY network configuration, including a perfectly configured public-HTTPS callback.
Evidence: ThothOS side: ThothOS-ai-native/src/lib/webhooks/dispatch.ts:126-127 (sign body only), 151-153 (always sends X-Webhook-Signature + X-Webhook-Timestamp); webhook.helpers.ts:26-28 (signPayload = HMAC over payload string alone), 40 (failureCount<5 filter), 68-82 (recordWebhookFailure $inc). Go side: Network-Monitor/internal/api/webhooks.go:350 (timestamp header presence forces timestamped branch), 362-367 (expects computeWebhookHMACWithTimestamp, 401 on mismatch), 238-244 (pre-image = timestamp + '.' + body), 373 (legacy body-only branch only when header absent).
Scenario: Operator sets PROXY_CALLBACK_URL=https://public.example.com, registers via the settings flow, then someone runs the triggerProxyConfigSync mutation. ThothOS POSTs the config with X-Webhook-Signature=HMAC(secret, body) and X-Webhook-Timestamp set → Go receiver computes HMAC(secret, ts+'.'+body), signatures differ → 401 → ThothOS records failure; after 5 events the webhook row hits failureCount=5 and is silently excluded from all future dispatch. Zero webhooks are ever accepted.

## [P1-broken] Callback URL is undeliverable in every default configuration, and registerWebhook accepts it silently — misleading registration success for NAT'd proxies
source: contract:webhook-realtime
The auto-detected callback is always http://<LAN-IP>:<port>: the boot path hardcodes callbackURL := "" and NEVER reads PROXY_CALLBACK_URL (only the MFA-login and settings-connect paths read the env var, both also defaulting to http://LAN-IP). ThothOS's send-time SSRF gate (validateCallbackUrl in dispatch.ts) requires https: AND rejects localhost/10./192.168./169.254./172.16-31. hosts — so the default URL can never receive a dispatch; each attempt records 'Rejected: unsafe callback URL' as a failure, and at failureCount>=5 the webhook is dropped from dispatch.
